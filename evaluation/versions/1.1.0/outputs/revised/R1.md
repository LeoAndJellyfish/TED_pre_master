# 支付超时后的重试

付款页面等了十秒，显示超时。如果用户再点一次，刚才那笔付款会怎样？我们来看一套合成的支付接口规格，用一次假设操作，说明重复扣款的风险怎样出现，以及接口怎样降低这个风险。

假设用户要支付一百元。点击付款后，网页发送请求，开始等待回复。用户正在操作的网页或应用，称为客户端；另一端接收请求、处理支付并返回结果，称为服务器。

十秒过去，客户端显示超时。服务器可能已经处理了支付，只是回复在途中丢失。页面上的提示告诉我们，十秒内没有收到回复，付款结果还要确认。

[画面：付款请求到达服务器，服务器已处理支付，返回的回复在途中丢失；客户端等到十秒，显示超时。]
[演示 10秒]

如果重试时又创建一笔新的支付请求，服务器就可能再处理一次付款。第一次已经处理、回复却丢失，加上第二次的新请求，就形成了重复扣款的风险。

这套规格要求，同一笔业务付款从首次发送到后续重试，都携带同一个识别标记，技术上称为幂等键。回到这一百元：第一次发送时使用键 A，超时后重试，仍然使用键 A，并保持原来的请求内容。服务器据此继续核对已经登记的那笔付款。支付已经完成、结果已经保存时，服务器就返回保存的结果。

服务器查找这项记录时，要同时看账户和键。因此，键 A 要连同所属账户一起识别；不同账户各有自己的记录。产品流程需要保存首次请求使用的键和内容，后续重试才能沿用。

同一个键也要对应相同的内容。仍以这次假设付款为例，一百元与键 A 再次发送，符合这项规则。金额如果改成一百二十元，却继续使用键 A，服务器会拒绝，因为这个标记对应的付款内容发生了变化。用户调整金额后，产品流程要先明确这是哪一笔业务，再安排提交。

有时，两次请求会几乎同时到达。假如服务器先分别查看记录，再分别开始处理，两个请求可能都在对方留下记录之前进入支付流程。同一个键要发挥作用，服务器就要在一个完整步骤中检查并占用该账户下的键。这个要求称为原子地占用：其他同时到达的请求也必须遵守同一项键记录。

占用之后，服务器还要记录处理中状态，最后保存处理结果。这样，并发到达的重试也沿着同一笔业务的记录处理。处理中记录说明这笔业务正在处理；最终结果供后续同键、同内容的请求返回。

[画面：两个请求指向同一条“账户＋键”记录，记录从“处理中”更新为“最终结果”。]
[停顿 5秒]

客户端每次重试都更换键，会创建新请求。

另外，键记录保留二十四小时。在记录保留期间，服务器依据它执行同键规则。二十四小时过后，记录可能失效，处理这类历史付款前，应先核对实际支付状态，再决定后续操作。这套规则针对同一账户下、二十四小时内保留的键记录。跨系统、无限期的唯一支付保证，规格没有提供。

回到超时后的重试：继续发送原键和原内容，服务器就能沿用这笔付款的记录。评审这套流程时，还要核对两个条件：同时到达的请求是否遵守同一记录，记录是否仍在二十四小时保留期内。
